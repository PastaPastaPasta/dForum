# Contract changes for NEXT registration

**The live testnet contract (`ozZNp21WNWLx79aJXFo2ScEaMtBc9vvfUonqmzADM16`) must NOT be changed.** Indexes are frozen at creation in protocol 14, and the contract is live — every change below is for a future contract registration. Nothing in this file changes this deployment.

## Structural changes

1. **Orphan index** — add `post.byThreadAuthor` (`threadId asc, $ownerId asc, $createdAt asc`) so the orphan rule is one bounded query per thread (`limit 1`) instead of the current bounded paginate of `byAuthor` ($ownerId, $createdAt) with client-side threadId filtering. The live app works today — this is a correctness/efficiency win at next registration.
2. **Drop the unused indexes** — `thread.byTag` (tags, $createdAt), `post.byForum` (forumId, $createdAt), `forum.byCategory` (categoryId, sort), `reaction.byPostKind` (postId, kind) → keep only `reaction.byPostOwner` (unique) + a `rangeCountable` byPostKind or a post-level count via `documents.count` with `where: { threadId: [threadId] }`; `report.recent` ($createdAt); `thread.byUpdated` and `post.byUpdated` ($updatedAt). `thread.moderated`/`post.moderated` stay (audit view).
3. **Drop the unused types** — `forumSettings` (the app reads nothing from it; one doc per deployment, unused everywhere), `teamMember` (display metadata, nothing renders it — no member page exists), `reaction` (no reaction UI), `report` (no report UI in the app; the console moderates threads/posts/profiles). Keep the `report` type only if a report UI is being planned — otherwise remove.
4. **`post.canBeDeleted`** — a post hidden by a moderator (modState) is currently deletable by its owner (canBeDeleted: true). Either set `false` (deletion only by moderators) or keep `true` with the honest note that authors can erase hidden posts. The current app hides posts, never deletes them — set `false`.
5. **`slug` immutable** — `forum.slug` and `category.slug` are mutable today (a rename would break every inbound link). Make both immutable at next registration.
6. **`avatarUrl` minLength-0 contradiction** — the property is declared `string(0, 300, { pattern: '^https://...' })` with minLength 0, meaning an empty string violates the https pattern (empty string matches `^https://` only if the pattern allows empty — it does not). Either declare minLength 1 (forces every profile to have a URL) or drop the pattern. Recommend: drop avatarUrl entirely (no avatar UI in the app; the avatar derives from the identity hash) or set minLength 1.
7. **`referenceKindFor` partial mirror** — `reaction.postId` refersTo post (deletableDocument) AND `forum.categoryId` refersTo category (permanentDocument) AND `thread.forumId`/`post.forumId` refersTo forum (permanentDocument) and `post.threadId` refersTo thread (moderatedDocument) — the three referenceKind forms are only exercised through `contracts/build.mjs`. The next registration should regenerate the contract from the in-repo source (`contracts/build.mjs`) and diff exactly against `contracts/generated/dforum.team.json`.
8. **`forumSettings.rules` maxBytes inert** — maxLength 1000 already caps the value below the 5120-byte platform cap; maxBytes is a no-op. Use maxLength 4000 + maxBytes 5120 or drop maxBytes.
9. **`hideBannedContent` inert** — declared in the contract; the SDK (5.1.0-rc.1) cannot read the banlist (`sdk.contracts.moderationEntries` throws a WASM binding error), so the app cannot honor it today. Either drop it or the app reads the banlist via an SDK fix + `moderationEntries` support.
10. **Network-mode roster read** — `getRoster()` reads `sdk.moderationCharters.team(contractId)` for the team members; for network mode the same call should be made with the elected moderation charter — verify the correct read against the network-mode contract at next registration.
11. **50-cap lists ordered** — the snapshot and clients cap forum/category at 50 with a completeness gate, but page through the index until dry instead (see scripts/snapshot.mjs). At next registration, ordering by `sort` should be via the index, not the window.
12. **`transitionSha256` in deployments** — the deployments record should carry the transition hash of the registration transaction (bind the exact contract bytes to the deploy) so the registration is verifiable offline.
13. **`report` in deletable types** — report is deletable at the contract level today but the app neither creates nor moderates reports. If reports stay in the contract, the moderation console must expose them; otherwise drop the type at next registration.
